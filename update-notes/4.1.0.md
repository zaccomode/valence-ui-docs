# 4.1.0

4.1 is a bug-fix release: it closes out the defect list that shipped alongside 4.0 (tracked in the library's `docs/V4-RELEASE-FIXES.md`) plus a handful of issues found afterwards. There are no new components and no intentional API removals beyond the two called out below, both of which were bug fixes with a behavioural edge.

Some of what's listed below was still open for review as PRs against the library's `v4` branch at the time these notes were written — check the linked issue/PR for current status if you're relying on a specific fix landing.

## Breaking changes

### Disabled buttons are now actually disabled

Every Valence button composes `PrimitiveButton`, which previously styled a `disabled` button without ever forwarding `disabled` to the underlying DOM element — so a "disabled" button was still clickable, focusable, and invisible to screen readers. `disabled` (or `aria-disabled` plus a suppressed click handler, for polymorphic targets that render an `<a>` or router `Link`) is now genuinely enforced.

If you were relying on a disabled button's `onClick` still firing — intentionally or not — that stops working. This also affects every component built on `PrimitiveButton`: `PillSelector` (its add button, and pill clicks when `allowClear={false}`), `SegmentedControl`, and so on.

### `UnstyledButton`'s `motion` prop is gone

`UnstyledButton` was the one component still on the pre-4.0 `motion` prop and `getMotionBehaviour` helper after everything else moved to `animation` / `useAnimation` in 4.0. It's now migrated, and `motion`, `getMotionBehaviour` and the `MotionBehaviour*` types are removed from the public API.

```tsx
// before
<UnstyledButton motion={{ onHover: "grow" }}>Bare</UnstyledButton>

// 4.1
<UnstyledButton animation={{ hoverAnimation: "grow" }}>Bare</UnstyledButton>
```

Unlike `PrimitiveButton`, `UnstyledButton` still applies no default hover/tap animation — matching the old prop's inert-unless-asked behaviour.

## Behaviour changes

### Components no longer "pop in" when a screen first appears

`Icon`, `Loader`, `Alert`, `Text`, buttons and `Slider`'s thumb all accept an `animation` prop that plays an enter transition on mount. Previously that transition played on *every* mount, including the very first paint of a page or modal — so opening a screen with a dozen animated icons and buttons on it made all of them visibly pop in at once.

As of 4.1, anything already on screen when the app first paints renders directly into its resting state, with no enter transition. Anything that mounts later — a toast, a modal opened by a user action, an item added to a list interactively — still animates in exactly as before. This needed no prop or API changes; if you weren't relying on the old mass pop-in effect, there's nothing to update.

## Fixes

**Correctness / crashes**

* `Card` could fail to render at all, and `ButtonWithIcon` could throw with `loading` set, depending on module evaluation order — caused by internal barrel-import cycles.
* `NumberInput` emitted `NaN` to `setValue` when the field was cleared, producing a React controlled-input warning and an unrecoverable field.
* `SelectInput` matched its `value` against `options` by reference (`===`), so a structurally equal value (the normal case, once it's round-tripped through state or JSON) would throw instead of resolving. Its first option's icon was also silently dropped due to a falsy-index check.
* `Icon` crashed if given a plain string, number, or multiple children instead of a single element.
* The library read `window` during render (`useWindowSize`, `useColorScheme`, and a `BottomSheet` default), so importing any component into a Next.js or Remix server component crashed outright. Server rendering now works; the SSR breakpoint resolves to each component's `default` responsive variant, and `useColorScheme` reports light on the server.
* `NumberInput`'s stepper buttons logged `Invalid prop 'size' supplied to React.Fragment` on every render — `InputContainer` was wrapping its `button` slot in `<Icon>`, which only expects a single icon element.
* `DropdownContainer` had stale typeahead matching after `options` changed, silently dropped responsive props and ref forwarding, let a caller's `onClick` clobber floating-ui's open/close handling, and could still be opened via pointer or keyboard while `disabled`.

**Props silently dropped**

* Passing a single `colors` entry to `ValenceProvider` replaced the entire default palette instead of extending it — breaking every component that resolves a built-in color by key (materials, etc). Custom colors now extend the palette, with a caller's color winning over a built-in of the same key.
* `Slider`, `RangeSlider` and `Switch` discarded `id`, `className`, `aria-*`, `data-*` and other unnamed props; `Switch` also ignored explicit `width`/`height`, and neither slider forwarded `disabled` to the underlying control.
* `ColorPicker` had the same class of bug — every prop it didn't explicitly name (`id`, `className`, `data-*`, `aria-*`, event handlers) was dropped.
* `Icon`'s animated render path dropped a child's own props entirely (unlike its non-animated path, which merges them) — this affected the `icon` prop on every input component in the library, since `InputContainer` always renders its icon slot animated.
* A disabled `InputContainer` still focused its input (and still fired `onClick`) when clicked.
* `PillSelector` only checked `maxSelectable` when adding a pill, not when clicking an existing one to select it.

**Type-only fixes** (no runtime change)

* `IconButton`'s `tooltipProps` typed away the ability to pass a controlled `disclosure`, even though it worked at runtime.
* `CardProps` didn't include a typed click handler even though `Card` renders a clickable `PrimitiveButton` under the hood.
* `AvatarProps["src"]` was required even though `undefined` renders the placeholder correctly.
* `Material.setInteractive` / `setOverrides` / `setChildrenOverrides` returned the base `Material` type, breaking subclass method chaining. `SolidMaterial` was also missing `setColor` and `PaperMaterial` was missing `setBlur`.

**Other**

* `useDisclosure` and `useControlledList` updated state from a stale closure, so two calls made in the same batch (e.g. two `toggle()`s, or an `add()` and a `remove()`) could collapse into one.
* `useElementSize` only re-measured on window resize, missing element-only size changes (layout shifts, content changes) — it now uses a `ResizeObserver`.
* `getSize("radius", …)` fell back to the theme's `size` default rather than its `radius` default — invisible out of the box, since the two coincide, but wrong for a theme that sets them apart.
* `Text` used an array as the React key driving its formatting change-animation, which only actually varied for unformatted plain text. Separately, every formatted segment (bold, italic, monospace, line breaks) was keyed with a fresh random id on every render, so they all unmounted and remounted needlessly on every re-render — destroying any animation, focus, or selection state inside formatted text.
* `Icon` called the deprecated Motion `motion(Component)` factory, logging a deprecation warning on every animated icon.
* `Textarea` set `verticalAlign: "center"`, which is not a valid CSS value and was silently dropped by browsers; it's removed rather than "corrected", since it never had any visual effect to preserve.
* `Material.copy()` was documented as a deep copy but shared its `overrides` / `childrenOverrides` objects with the original, so mutating a copy could reach back into its source.
* `UseWindowTitle` (PascalCase) didn't read as a hook to React's lint rules; it's renamed to `useWindowTitle`, with the old name kept as a deprecated alias.
* `SliderTrackProps.material` was declared but never applied.
* `Switch` had no `role="switch"` / `aria-checked`, and its label wasn't associated with the control for assistive tech.
* `npm run build` never cleaned `dist/` before rebuilding and didn't stop emitting on a type error, so a partial or failed build's stale output could ship to npm alongside a later successful build.
* A `tsconfig` change made partway through the 4.1 cycle (switching `moduleResolution` to `"bundler"` to fix an unrelated `rootDir` build error) broke the CommonJS build target, since `bundler` resolution isn't valid alongside `module: "CommonJS"`.

## Migration checklist

1. Check anywhere you render a `disabled` button (or a component built on one — `PillSelector`, `SegmentedControl`, etc.) for code that relied on clicks still firing while disabled.
2. Replace any `motion` prop on `UnstyledButton` with `animation`, using the mapping in [4.0's migration notes](4.0.0.md) for the equivalent shape.
3. If you were passing a single-entry `colors` array to `ValenceProvider` as a workaround for the palette-replacement bug, you can drop the `DEFAULT_PALETTE` spread now — it's additive by default.

Everything else in this release is a straightforward bug fix with no caller-visible change beyond "the thing that used to be broken now works."
